## 一、审计目标

本台账用于持续记录 `JobsDocs` 的查漏补缺进度。审计标准不是“作者目前知道什么”，而是尽量还原知识对象本身的边界、前提、例外和失败模式，并让读者能够验证、执行、诊断和恢复。

任何主题只有同时满足下列条件，才标记为“已审计”：

1. **事实正确**：命令、参数、对象关系和因果表述能够被官方文档、标准、源码或可复现实验支持。
2. **范围完整**：同时说明正常路径、边界条件、常见误区、故障诊断、恢复办法和不可逆风险。
3. **时效明确**：易变化内容标注验证日期、适用版本或直接链接到权威入口，避免把当前状态写成永恒事实。
4. **来源分级**：官方规范和实现高于二手文章；个人经验必须标明适用环境，不能冒充通用结论。
5. **可以执行**：示例包含前置条件、预期结果、验证方法和失败后的停止点。
6. **安全合规**：不公开 Token、私钥、Cookie、个人身份信息或可被直接滥用的凭据；破坏性命令必须先解释影响和备份方式。
7. **内部一致**：目录入口、标题、术语、链接、图片、代码块和相互引用保持一致，不让同一概念在不同文章中互相冲突。

## 五、安全优先事项

### 5.1、已处理但仍需要仓库外动作

旧版 GitHub Actions 教程截图曾显示完整的 classic personal access token。当前工作树中的图片已经遮蔽，但仅修改现行文件不能让已泄露凭据恢复安全，也不会自动清除 Git 历史、Fork、缓存或旧制品中的副本。

应立即完成：

1. 在 GitHub 撤销或轮换该 Token。
2. 检查该 Token 的权限范围、最后使用时间和相关审计日志。
3. 评估是否需要经过备份和协作确认后重写仓库历史；历史清理不得在未确认影响范围时直接执行。

### 5.2、已发现、未擅自修改

下列被 Git 跟踪的依赖目录中存在一把语法有效的私钥：

```text
iOS相关的文档和资料.md/直播推流:拉流@Swift5x.md/local-live-server/
node_modules/node-media-server/bin/privatekey.pem
```

它位于第三方 `node_modules`，因此本轮没有改动。后续安全批次需要确认它是否只是上游演示证书的配套私钥、是否被任何本地服务实际使用，以及整个 `node_modules` 是否有必要继续纳入文档仓库。无论来源如何，都不得把仓库内这把私钥用于真实环境。

Fastlane 文件中出现的 PEM 头只是把外部 `key_content` 包装成私钥文本的代码，不是仓库内嵌的真实私钥；网页快照中的同类命中来自加密库生成 PEM 文本的实现。这两类已判定为结构性误报。

## 六、后续审计顺序

1. **P0：安全与可恢复性**——凭据、私钥、部署脚本、自动化工作流、破坏性命令和外部发布入口。
2. **P1：高频工程知识**——iOS、macOS、Shell、依赖管理、构建、签名、网络和常见故障。
3. **P2：体系化完整度**——概念模型、版本边界、错误案例、验证实验、跨文章冲突和缺失入口。
4. **P3：历史资料治理**——网页快照、第三方资料、重复图片、失效外链、归档价值和版权来源。

每完成一个批次，都要在本台账追加：范围、文件数量、关键缺口、事实修正、来源、验证结果、遗留风险和下一批入口。

## 七、来源反向映射规则

文档审计不能只在 `JobsDocs` 内自循环。对会影响实际开发流程的主题，应主动反查：

- Jobs 自有脚本、Demo、配置仓库和实际工程中的可执行实现；
- 对应工具的官方手册、标准、发行说明和源码；
- 真实故障日志、恢复记录和可复现实验；
- 现有文章没有覆盖、但实现已经承担的异常分支。

本次 Git 批次正是依据这一规则，把 `SourceTree.command` 中的 Commit、Fetch 修复能力补回知识库，而不是等已有文章先提到它们。
